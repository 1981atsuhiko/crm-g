## 1. 計画の方針
計画の項目には `TPL-xxx` を付ける。要件定義書・設計書にない判断は、9章に `TPD-xxx` として一覧にする。確認できていない内容は `TBD:` とする。

| ID | 方針 | 内容 | 根拠 |
|---|---|---|---|
| `TPL-001` | 範囲 | フェーズ1の全機能と、DB・移行・配布の非機能を対象にする。対象外は、次のとおり。①実データでの確認（`TPL-050`）。②非機能の合否（起動時間・常駐メモリ・配布物のサイズは、数値の目標を設けない。再計算の時間などは目標値が未決。`TC-NFR`）。③人事連携の受け取り側の処理 | ユーザーの回答（2026-10-21）、`ARC-022` |
| `TPL-002` | 試験の基準 | 試験は、要件 ID と設計 ID にひもづける。期待値は、設計書の固定値（数値例・表）を使う。根拠のない期待値を作らない | 成果物ルール（ID でトレースできるようにする） |
| `TPL-003` | リポジトリルールの適用 | ①検証コードにロジック（条件分岐・ループ・計算）を書かず、`parametrize` で固定値を与える。②試験は独立して実行でき、順序や外部状態に依存しない。③単体試験では、外部依存（DB・ファイル・ネットワーク・時刻）をモックか入力値に置き換える。④試験コードにも `ruff` と `mypy`（strict）を適用し、警告ゼロにする | コーディング規約、Python 実装ルール |
| `TPL-004` | 暫定の期待値 | 設計書の `TBD:` や暫定の扱い（例：計算仕様書 12章）に依存する試験は、「暫定」と明記する。決まったら、設計書と本書を同じ変更で更新する | 成果物ルール（未確定事項は `TBD:`） |
| `TPL-005` | 本書で扱うケースの ID | 設計書が定めた `TC-CLC`・`TC-SCD`・`TC-SCN`・`TC-MIG` は、そのまま使う（5.2）。設計書にない観点は、本書で `TC-CAL`・`TC-FUN`・`TC-DBD`・`TC-ARC`・`TC-E2E`・`TC-NFR` として追加する（5.3〜5.7）。ID は変更・再利用しない | `TPD-006` |

## 2. 試験レベル

### 2.1 試験レベルの定義 `TPL-010`
| レベル | 略称 | 対象 | 外部依存 | 実施の方式 |
|---|---|---|---|---|
| 単体試験 | UT | ドメイン層（計算）、入力の検証・変換（日付・金額・名寄せの正規化）、表示の整形、設定ファイルの読み込み | なし。時刻・DB・ファイルは、モックか入力値で与える | 自動（`pytest`） |
| 結合試験 | IT | アプリケーション層とインフラ層。実際の SQLite（一時ファイル）、一時ディレクトリのファイル、ログファイルを使う | DB とファイルは実物。時刻は固定値に差し替える | 自動（`pytest`） |
| システム試験 | ST | UI 層を含む、画面の操作・起動・配布物。移行コマンドのプロセス | 画面は `AppTest`（ブラウザなし）。自動にできないものは手動 | 自動（`AppTest`、プロセス起動）または手動 |
| 非機能試験 | NF | 起動時間・常駐メモリ・配布物のサイズ・再計算時間・ログ容量 | 配布物（exe）を実機で動かす | 手動（測定） |
| 受入試験 | AT | 業務シナリオ（`TC-E2E`）を、利用者が実施する | 配布物（exe）と、架空のデータ | 手動 |

- 結合試験で実際の SQLite を使うことは、リポジトリルール「単体試験では外部依存をモックに置き換える」の対象外とする。データ設計書の制約（`STRICT`、`CHECK`、外部キー、トリガー）は、実際の SQLite でしか確かめられないため（`TPD-004`）
- 画面（UI 層）は、業務ルールを持たない（`ARC-002`）。画面の試験は、表示と操作の振る舞いに絞る。計算結果の正しさは、単体試験と結合試験で確かめる

### 2.2 自動と手動の分担 `TPL-011`
| 方式 | 使う場面 |
|---|---|
| 自動（`pytest`） | ドメイン層、検証、DB の制約、トランザクション、操作ログ、マイグレーション、移行の取込、ファイル出力 |
| 自動（`AppTest`） | Streamlit の画面の表示・入力・ボタン・エラー表示。`AppTest` はブラウザを使わず、1回に1ページだけを実行する（公式ドキュメント）。ページをまたぐ状態は、`session_state` に直接設定して再現する |
| 自動（プロセス起動） | 移行コマンドの終了コード、多重起動の拒否。`subprocess` は、`shell=True` を使わずに起動する |
| 手動 | ブラウザの実際の挙動（URL の直接入力、新しいタブ）、別の PC からの接続、Excel での表示、配布物（exe）の起動・手順書の確認、非機能の参考値の記録 |

- PoC（実装計画書 `POC-05`。Windows、Streamlit 1.66.0）で、`AppTest` で扱えたものは次のとおり。`switch_page`（登録済みのページのスクリプトを指定）、`file_uploader`、`download_button`（要素の存在のみ。ダウンロードされる内容は確認できない）、`st.data_editor`（`dataframe` として）、`st.date_input`（`value=None`）、`st.dialog`（開いた後の内容）。認証前に、保護されたページへ `switch_page` すると、`ValueError` になった。ブラウザの実際の挙動（URL の直接入力、ダウンロード）は、手動の試験にする。`TBD:` 11章-3 のうち、上記以外の挙動は、実装時に確認する

## 4. 試験データ

### 4.1 方針 `TPL-030`
- 試験データは、架空のデータだけを使う。実在の人名・メールアドレス・金額を使わない（成果物ルール）
- 氏名は、明らかな架空の名前（例：`試験 一郎`、`試験 花子`）にする。メールアドレスは、予約済みのドメイン（`example.com`）にする
- 試験データを、リポジトリに含めてよい。個人情報・秘密情報を含めない

### 4.2 データの種類 `TPL-031`
| 種類 | 内容 | 使う試験 |
|---|---|---|
| 計算の数値例 | 計算仕様書 9章の `EX-001`〜`EX-010`。入力と期待値は、計算仕様書の表のとおり（固定値） | `TC-CLC`、`TC-FUN-011` |
| 計算の追加の入力 | 5.3 の各ケースの「入力」に書いた値。計算仕様書の数値例にない境界を、端数が出ない値で作る | `TC-CAL` |
| 取込用 CSV | 取込の種類（`IMP-01`〜`IMP-06`）ごとに、正常のファイルと、エラー（`E001`〜`E019`）を1つずつ起こすファイル。文字コード（UTF-8 BOM 付き・なし、Shift_JIS）の違うファイルも用意する | `TC-MIG` |
| 画面・業務の標準データ | 社員 10名程度（在籍・退職予定・退職・年俸制を含む）、給与履歴、稼働期間、単価履歴、月次結果。業務シナリオで共通に使う | `TC-FUN`、`TC-E2E` |
| 営業日カレンダー | 試験で使う月の営業日を、入力として与える。祝日は、`jpholiday` を呼ばず固定値にする（`ARC-012`：ドメイン層は `jpholiday` を呼ばない） | `TC-CLC`、`TC-CAL` |
| 旧版の DB | マイグレーションの試験用に、1つ前の版のスキーマの DB を作る | `TC-ARC-009`〜`TC-ARC-014`、`TC-E2E-006` |

### 4.3 固定する値 `TPL-032`
- 時刻は、固定値（例：`2026-10-21T00:00:00Z`）に差し替える。`datetime.now()` を試験の中で使わない
- 祝日の取込（`TC-ARC-019`）だけは、`jpholiday` の実物を使う。期待値は、元日（2026-01-01）が祝日になることだけにする
- 乱数を使わない。計算仕様書 `TC-CLC-010` は、試作で乱数 20,000 ケースを確認した。実装後は、固定値の入力で検証する（計算仕様書 10章）

## 6. 実施と完了の基準

### 6.1 実施のタイミング `TPL-060`
| タイミング | 実施するもの |
|---|---|
| 実装の都度（PR ごと） | 自動試験の全件（UT・IT・ST の自動）、`ruff`、`mypy`、カバレッジの測定 |
| 計算・移行・DB を変えたとき | 該当の `TC-CLC`・`TC-CAL`・`TC-MIG`・`TC-DBD`・`TC-ARC` を、必ず実行する（全件に含まれる） |
| リリースの前 | 手動の試験の全件（ST の手動、`TC-ARC` の手動）、`TC-NFR`、`TC-E2E`（受入） |

### 6.2 完了の基準 `TPL-061`
次をすべて満たしたとき、試験を完了とする。

1. 計画した全ケースが、合格している。`TBD:` により判定できないケースは「保留」とし、理由をテスト結果報告書に書いて、ユーザーの承認を得る
2. 自動試験が全件合格している
3. `ruff` と `mypy`（strict）が、警告ゼロである
4. カバレッジが、`TPL-062` の基準を満たしている
5. コードの実装後に、サブエージェントでセルフレビューを行い、対応結果を報告している（`TPL-063`）
6. 重大な不具合が、未解決のものがない（`TPL-064`）

### 6.3 カバレッジの基準 `TPL-062`
ユーザーの回答（2026-10-21）に基づく。

| 層 | 基準 |
|---|---|
| ドメイン層 | 100% |
| アプリケーション層 | 80% 以上 |
| UI 層・インフラ層 | 目標を定めない（測定し、報告する） |

- 測定は、`coverage.py` の分岐カバレッジ（`--branch`）を有効にして行う。基準の値は、行と分岐を合わせた値とする（`TPD-002`）
- 層ごとの値の集計は、`coverage report --include` と `--fail-under` で行い、基準を下回ったときは終了コードで失敗させる方法とする（実装計画書 `IPL-023`、`IPD-011`。承認済み 2026-10-22）。小数を含めた厳密な判定は、実装計画書 `PH-01` で確認する（11章-2）
- カバレッジは、試験の網羅の目安である。基準を満たすために、検証のない試験を書かない。基準を満たすために、試験の削除・弱体化・期待値の書き換えをしない（リポジトリルール）

### 6.4 セルフレビュー `TPL-063`
- コードを実装した後は、完了を報告する前に、必ずサブエージェントでセルフレビューを行う（リポジトリルール）
- 指摘は、内容を確認して対応する。報告に、修正した点と、修正しなかった点とその理由を含める
- 試験コードも、セルフレビューの対象に含める。確認項目は、次のとおり
  - 検証コードにロジックがない（`TPL-003`）
  - 期待値が、設計書の固定値と一致している
  - 試験が、順序・外部状態に依存しない
  - `TC-ARC-003` の確認（キャッシュの不使用）

### 6.5 不具合の扱い `TPL-064`
暫定の扱いである（`TPD-008`）。ユーザーの確認後に、確定する。

| 区分 | 内容 | 対応 |
|---|---|---|
| 重大 | 計算結果の誤り、データの消失・不整合、機微情報の漏えい、認証の回避、起動不能 | 完了までに、必ず修正する |
| 通常 | 上記以外で、仕様と異なる振る舞い | 修正するか、`TBD:` として残すかを、ユーザーが判断する |

- 不具合を見つけたら、再現する試験を追加してから、修正する（コーディング規約：バグ修正時は再現テストを追加する）
- 不具合は、GitHub の Issue で管理する案とする（`TPD-008`）

### 6.6 試験結果の記録 `TPL-065`
- 実施の結果は、実装後に `Docs/テスト結果報告書_vX.Y.md` に記録する（`TPD-009`）。記録する項目は、実施日・版・ケース ID・結果（合格・不合格・保留）・不具合の ID・保留の理由とする
- 自動試験の結果は、実行したコマンドと、合格・不合格の件数、カバレッジの値を記録する
- 試験結果に、実データ・個人情報を含めない
